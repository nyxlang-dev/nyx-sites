std/pdf writes a real PDF in pure Nyx, letter size here, with positions in MILLIMETRES from the top-left corner — the module does the conversion to points and the vertical flip PDF expects. This recipe builds a full invoice: an issuer header with a PNG logo, a buyer block, a line-item table made of text and line calls (the spec is explicit that a table is a recipe, not a function of the module, because its layout decisions belong to the caller), right-aligned totals with 16% tax, and a QR from std/barcode drawn module by module with rect.

factura: 26456 bytes, empieza con %PDF-1.4 para escribirla: nyx run -- factura.pdf

Every amount is worked in CENTS, as an int — never a float — and monto formats it with Venezuelan separators (. for thousands, , for the decimal pair). mul_div_round(base, 16, 100, RoundMode.HalfUp) computes the tax with the rounding rule spelled out, instead of trusting whatever a float multiplication happens to land on for a specific amount.

texto_der right-aligns a piece of text against a fixed edge by measuring it first with pdf_text_width(s, f, pt) and placing it at edge - width — the same primitive lines up every column of the table and every total without a single hardcoded x per row. pdf_text_supported(cliente) is asked BEFORE drawing a name that could carry a character outside the standard fonts' coverage (an emoji, another alphabet): text() would fail turning the document into bytes(), so the recipe substitutes a safe placeholder instead of letting the whole invoice fail on one field.

The logo comes from include_bytes(...), so the PNG travels inside the compiled binary — no file to ship alongside it, in native or in wasm32-wasi. The QR at the bottom is std/barcode's qr_matrix, walked row by row: consecutive dark modules in a row become ONE rect instead of one per module, so there is no seam between them and fewer drawing operations. d.bytes() is the single point that can fail — anything that could not be drawn exactly as asked comes back as an Err, not a silently wrong PDF.
