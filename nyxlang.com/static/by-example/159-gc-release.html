Returning memory to the system with std/gc

The collector frees what is unreachable, but it keeps those pages for reuse and does not hand them back to the system: after a peak (a huge response, a large batch) a long-lived process keeps occupying whatever it managed to map. std/gc provides gc_release(), which collects and returns the heap's free pages to the system, and two gauges: gc_heap_bytes() (mapped heap) and gc_free_bytes() (free inside it).

// Nyx by Example: devolver memoria al sistema tras un pico con std/gc.
//
// El GC reutiliza la memoria que libera, pero no la devuelve al sistema por su
// cuenta: tras un pico (una respuesta enorme, un lote grande) el proceso sigue
// ocupando lo mapeado. En un servidor de larga vida, `gc_release()` colecta y
// devuelve al sistema las páginas libres. Detiene todos los hilos mientras
// corre: llámala tras el pico, no en cada pedido. No existe en wasm.
// El GC es conservador: si justo después del pico un puntero viejo sigue en la
// pila, la primera llamada puede no soltarlo; la segunda sí (ver std/gc).
//
// En un servidor std/serve no hace falta llamarla a mano: NYX_SERVE_IDLE_RELEASE_SECS=30 la invoca solo
// tras 30 s sin pedidos (apagado por omisión; ver docs/SPEC.md, «Respuesta por trozos»).
//
// gc_heap_bytes() = heap mapeado; gc_free_bytes() = libre dentro de él.
import "std/gc"

fn pico() -> int {
    var trozos: Array = []
    var i = 0
    while i < 32 {
        trozos.push("y".repeat(1048576))
        i = i + 1
    }
    return trozos.length()
}

fn main() -> int {
    gc_release()
    let antes: int = gc_heap_bytes()
    let n: int = pico()
    let en_pico: int = gc_heap_bytes()
    println("trozos alocados: " + int_to_string(n))
    println("el heap creció: " + (en_pico > antes).to_string())
    gc_release()
    gc_release()
    let despues: int = gc_heap_bytes()
    println("tras gc_release el heap bajó: " + (despues < en_pico).to_string())
    println("libre >= 0: " + (gc_free_bytes() >= 0).to_string())
    return 0
}
Outputstdout
trozos alocados: 32
el heap creció: true
tras gc_release el heap bajó: true
libre >= 0: true

How it works

The program calls gc_release() to start from a clean heap and takes gc_heap_bytes() as a baseline. Then it allocates 32 strings of 1 MiB and measures again: the heap grew. After that it calls gc_release() twice and checks that the heap went down from the peak. gc_free_bytes() is an approximate figure that depends on the last collection, so the recipe only checks that it is not negative.

The second call is deliberate. The collector is conservative: if an old pointer is still in a register or on the caller's stack, the first call may not release the peak, and the second one does.

Limits: gc_release() stops ALL threads while it runs, so call it after the peak and not on every request; whatever a live variable or another thread's stack holds is not released; and std/gc does not exist on wasm32-wasi.

In a std/serve server you do not have to call it by hand. With the environment variable NYX_SERVE_IDLE_RELEASE_SECS=30 (off by default; a 0 or invalid value leaves it off) a server thread calls gc_release() after 30 s without requests. It has a cost: each release stops all threads while it runs, and the first large request afterwards takes longer. Also, with no traffic a floor of one body per worker stays until each worker serves another request. What avoids the peak at its root is not building the whole body: see the chunked response recipe.
