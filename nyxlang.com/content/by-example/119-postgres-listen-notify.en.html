With ONE process, sse_broadcast reaches every browser: the rooms live in that process's memory. With SEVERAL processes of the same program — to use more than one core, or to restart without dropping connections — each keeps its own rooms, and what process A writes never reaches a browser connected to process B. PostgreSQL's LISTEN/NOTIFY closes that gap with no extra moving part: whoever writes calls try_pg_notify INSIDE its transaction, so a browser never hears about a row that does not exist — the notification is delivered only on COMMIT, never on ROLLBACK — and every process keeps one dedicated connection that LISTENs and fans out what arrives to its own SSE rooms.

$ PORT=8081 ./app $ PORT=8082 ./app listening on :8081 listening on :8082 $ curl -d 'pedido 7 listo' localhost:8081/avisos ok $ curl -N localhost:8082/eventos/avisos event: aviso data: pedido 7 listo

guardar_aviso writes the row and calls try_pg_notify(conn, "avisos", texto) in the SAME transaction, so the two commit together or neither exists — the channel name is a quoted identifier, and "avisos" here has to match what try_pg_listen subscribed to exactly, accents included. The payload travels as text, capped at 8000 bytes by the protocol itself.

The guarantee that makes this safe under load is in std/postgres, not in this recipe: a notification that arrives while the listening connection is busy running another query is KEPT and handed over by the next try_pg_wait_notifications call — never lost, never mixed into that query's result rows. escuchar runs on its own thread with a dedicated connection, NEVER one taken from the pool: a pooled connection goes back to other handlers, and its LISTEN subscription would travel with it.

try_pg_wait_notifications(conn, 5000) blocks up to the given timeout and returns Ok([]) when nothing arrived — each element is [channel, payload, pid], the pid of the server process that raised the notification. If the connection dies (a server restart: Err with kind "connection"), the subscription dies with it, and escuchar's outer loop reconnects and issues LISTEN again.
