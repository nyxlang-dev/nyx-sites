A print-layout editor lets the user trace a pre-printed sheet — an invoice with its letterhead and boxes — by putting the sheet in the background and placing the fields on top. The print shop delivers the template as a PDF, so one page has to become an image on the server, shrunk and stored like any other picture. pdf_open reads the cross-reference table and the pages; doc.render_report(page, dpi, opts) draws one of them.

páginas: 1 página 1: 612.0 x 792.0 puntos imagen: 1275 x 1650 px fondo para el editor: 773 x 1000, 52416 bytes de JPEG rechazado: invalid: pdf_render: no es un PDF (falta %PDF- al principio) (code 22)

The sheet is built here with std/pdf so the recipe does not depend on a file; in real life it is the bytes the user uploaded. pdf_open validates the structure and counts the pages without drawing anything, and doc.page_size(1) gives the size in points (612 × 792 is US Letter). At 150 dpi that page becomes a 1275 × 1650 Image, which std/image then treats like any photo: image_resize_fit shrinks it to fit in 1000 × 1000 and image_encode_jpeg encodes it.

There are two modes. Strict (pdf_render_strict()) returns Err(unsupported) naming what the page uses and the renderer does not draw, so an image never comes out with a piece missing and no warning. Best effort (pdf_render_best_effort() with render_report) draws the rest and returns what it left out in res.omitted, so the caller decides whether it is good enough — a missing decorative gradient does not get in the way of tracing boxes. Bytes that are not a PDF give an Err with the reason, not a hang. The header of the .nx lists what is drawn (paths, clipping, the usual color spaces, JPEG and raw images, embedded TrueType/CFF fonts and the 14 standard ones) and what is not (shadings and patterns, Type 1 and Type 3 fonts, JBIG2/JPX/CCITT, encrypted files).
