Dos guardas contra el abuso. Un tope de cuerpo por ruta, en bytes: el tope global es NYX_HTTP_MAX_BODY (1 MiB) y una ruta puede ser más estricta o más holgada — app_max_body(app, "POST", "/contacto", 16384) para un formulario de contacto, 8 MiB para fotos. Por encima del tope la respuesta es 413. La receta hace de cliente con sockets TCP crudos para poder correr sola.

nyx-serve starting on 127.0.0.1:18214 with 2 workers 100-byte form: 200 101-byte form: 413 client ana, request 1: 200 client ana, request 2: 200 client ana, request 3: 200 client ana, request 4: 200 client ana, request 5: 429 client beto, request 1: 200

El parser lee hasta el mayor tope declarado por CUALQUIER ruta antes de que una ruta pueda rechazar, así que conviene subir un tope solo donde hace falta. El limitador cuenta por origen en una ventana fija y es COMPARTIDO por todos los workers del proceso (son hilos de un mismo proceso, protegidos por un mutex): app_rate_limit(app, 120, 60) para toda la app, app_route_rate_limit(app, "POST", "/contacto", 5, 60) para una ruta. Por encima del límite la respuesta es 429 con Retry-After en los segundos que faltan para cerrar la ventana — mira la petición 5 del cliente ana, mientras beto sigue recibiendo 200.

El origen es la IP del cliente, y detrás de un proxy inverso todas las peticiones llegan desde el proxy; se cuenta por otra clave con app_rate_limit_key(app, fn), por ejemplo rate_key_forwarded_for (el primer X-Forwarded-For) o un id de usuario. Una clave vacía exime a la petición. Los conteos son por proceso: dos instancias detrás de un balanceador cuentan por separado.
